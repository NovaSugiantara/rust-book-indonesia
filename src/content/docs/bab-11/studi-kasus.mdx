Sampai Bab 10, Kasir Warung punya validasi, perhitungan, dan error. Sekarang kita menambahkan test agar aturan itu tidak rusak saat kode berubah.

<StudyCase title="Kasir Warung: test aturan bisnis" intro="Menguji input, diskon, subtotal, dan pembayaran gagal.">
  <StudyCaseStep
    title="Test validasi input"
    goal="Memastikan input salah menghasilkan error yang tepat."
  >
    `parse_jumlah` mengembalikan `Result`. Test bisa memeriksa variant error tanpa mencetak pesan.

    ```rust
    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn jumlah_nol_ditolak() {
            let hasil = parse_jumlah("0");
            assert!(matches!(
                hasil,
                Err(KasirError::InputTidakValid(_))
            ));
        }

        #[test]
        fn teks_ditolak() {
            assert!(matches!(
                parse_jumlah("dua"),
                Err(KasirError::InputTidakValid(_))
            ));
        }

        #[test]
        fn jumlah_valid_diterima() {
            assert_eq!(parse_jumlah("3").unwrap(), 3);
        }
    }
    ```

    <Fragment slot="hint">
      `matches!` memeriksa pattern tanpa harus menangani seluruh variant. Cocok untuk test error.
    </Fragment>

    <Fragment slot="solution">
      Test memastikan input salah tidak berubah menjadi panic dan input valid tetap diterima.
    </Fragment>
  </StudyCaseStep>

  <StudyCaseStep
    title="Test perhitungan"
    goal="Menguji subtotal dan diskon dengan data yang mudah dibaca."
  >
    Buat helper kecil di module test untuk menyusun transaksi. Helper test boleh memakai nilai tetap.

    ```rust
    fn transaksi_contoh() -> Transaksi {
        let menu = HashMap::from([
            (
                "KOPI".to_string(),
                MenuItem {
                    nama: "Kopi".to_string(),
                    harga: 12_000,
                },
            ),
            (
                "ROTI".to_string(),
                MenuItem {
                    nama: "Roti".to_string(),
                    harga: 8_000,
                },
            ),
        ]);

        let items = vec![
            ItemPesanan::baru("KOPI", 1),
            ItemPesanan::baru("ROTI", 2),
        ];

        Transaksi::baru(String::from("Bu Sri"), menu, items)
    }

    #[test]
    fn subtotal_sesuai_menu() {
        let transaksi = transaksi_contoh();
        assert_eq!(transaksi.subtotal().unwrap(), 28_000);
    }
    ```

    <Fragment slot="hint">
      Fokuskan satu test pada satu aturan. Test subtotal tidak perlu memeriksa status pembayaran.
    </Fragment>

    <Fragment slot="solution">
      Dengan helper, test tetap pendek dan data uji tidak tersebar.
    </Fragment>
  </StudyCaseStep>

  <StudyCaseStep
    title="Test pembayaran dan integration test"
    goal="Menguji aturan pembayaran dan memakai API public dari luar crate."
  >
    Pembayaran kedua harus menghasilkan error. Integration test memakai library seperti pemakai luar.

    ```rust
    #[test]
    fn pembayaran_kedua_ditolak() {
        let mut transaksi = transaksi_contoh();
        transaksi.bayar(MetodeBayar::Qris).unwrap();

        let hasil = transaksi.bayar(MetodeBayar::Tunai);
        assert!(matches!(hasil, Err(KasirError::PembayaranGagal(_))));
    }
    ```

    File `tests/kasir.rs`:

    ```rust
    use kasir_warung::menu::ItemPesanan;

    #[test]
    fn item_pesanan_public_bisa_dibuat() {
        let item = ItemPesanan::baru("KOPI", 1);
        assert_eq!(item.subtotal(), 12_000);
    }
    ```

    <Fragment slot="hint">
      Integration test hanya bisa memakai item public. Kalau helper test private dibutuhkan, letakkan di unit test atau buat helper public khusus test.
    </Fragment>

    <Fragment slot="solution">
      Unit test menguji detail internal. Integration test memastikan API public tetap bekerja dari sudut pemakai crate.
    </Fragment>
  </StudyCaseStep>
</StudyCase>

## Keadaan setelah Bab 11

- Validasi input memiliki unit test untuk nol, teks, dan nilai valid.
- Subtotal diuji dengan menu dan item contoh.
- Pembayaran kedua diuji sebagai error.
- Integration test dapat memakai API public library.
- Perilaku aplikasi tidak berubah; test hanya menambah jaring pengaman.
- Belum ada test endpoint HTTP karena endpoint belum ada.

:::note[Kalau di bahasa lain]
Jest, go test, PHPUnit, dan pytest sama-sama memisahkan tahap arrange, act, dan assert. Rust memakai fungsi `#[test]` serta `assert_eq!`/`assert!`, dan integration test berada di crate terpisah. Konsepnya mirip, alatnya menyatu dengan Cargo.
:::
