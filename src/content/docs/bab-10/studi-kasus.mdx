Di Bab 9, pembayaran masih memakai enum dan method langsung di `Transaksi`. Sekarang kita membuat trait `PaymentMethod` agar metode pembayaran bisa diperlakukan sebagai perilaku, bukan tipe konkret. Kita juga menambahkan ringkasan yang meminjam data transaksi dengan lifetime.

<StudyCase title="Kasir Warung: pembayaran dan ringkasan" intro="Membuat trait pembayaran, fungsi generik, dan view yang meminjam transaksi.">
  <StudyCaseStep
    title="Buat trait PaymentMethod"
    goal="Mendefinisikan kontrak pembayaran yang bisa dipakai beberapa metode."
  >
    Trait menyimpan perilaku yang sama: label metode dan proses pembayaran.

    ```rust
    trait PaymentMethod {
        fn label(&self) -> &'static str;
        fn bayar(&self, total: u32) -> Result<(), KasirError>;
    }

    struct Tunai;

    impl PaymentMethod for Tunai {
        fn label(&self) -> &'static str {
            "tunai"
        }

        fn bayar(&self, total: u32) -> Result<(), KasirError> {
            println!("Menerima tunai Rp{total}");
            Ok(())
        }
    }

    struct Qris;

    impl PaymentMethod for Qris {
        fn label(&self) -> &'static str {
            "QRIS"
        }

        fn bayar(&self, total: u32) -> Result<(), KasirError> {
            println!("Memproses QRIS Rp{total}");
            Ok(())
        }
    }
    ```

    <Fragment slot="hint">
      Mulai dari method yang benar-benar berbeda antar metode pembayaran. Jangan memasukkan semua logika transaksi ke trait.
    </Fragment>

    <Fragment slot="solution">
      `PaymentMethod` adalah kontrak kecil. `Transaksi` tetap memiliki data pesanan; trait hanya mengurus proses pembayaran.
    </Fragment>
  </StudyCaseStep>

  <StudyCaseStep
    title="Fungsi generik pembayaran"
    goal="Memakai trait bound agar fungsi menerima metode pembayaran apa pun."
  >
    Fungsi generik bisa memanggil method trait tanpa mengetahui tipe konkretnya.

    ```rust
    fn proses_pembayaran<T: PaymentMethod>(
        metode: &T,
        total: u32,
    ) -> Result<(), KasirError> {
        metode.bayar(total)
    }
    ```

    Pemanggilan:

    ```rust
    proses_pembayaran(&Tunai, 43_000)?;
    proses_pembayaran(&Qris, 43_000)?;
    ```

    <Fragment slot="hint">
      `T: PaymentMethod` adalah trait bound. Tanpa bound, compiler tidak tahu bahwa `T` punya method `bayar`.
    </Fragment>

    <Fragment slot="solution">
      Satu fungsi bisa dipakai untuk `Tunai`, `Qris`, dan metode lain yang mengimplementasikan trait.
    </Fragment>
  </StudyCaseStep>

  <StudyCaseStep
    title="Ringkasan dengan lifetime"
    goal="Membuat view ringkasan yang meminjam nama pelanggan tanpa clone."
  >
    `Ringkasan` menyimpan reference ke nama pelanggan. Lifetime `'a` memastikan ringkasan tidak hidup lebih lama dari transaksi.

    ```rust
    struct Ringkasan<'a> {
        pelanggan: &'a str,
        subtotal: u32,
    }

    fn buat_ringkasan<'a>(
        transaksi: &'a Transaksi,
    ) -> Result<Ringkasan<'a>, KasirError> {
        Ok(Ringkasan {
            pelanggan: &transaksi.pelanggan,
            subtotal: transaksi.subtotal()?,
        })
    }
    ```

    <Fragment slot="hint">
      Hasil `buat_ringkasan` meminjam `transaksi`. Pemanggil tidak boleh memakai ringkasan setelah transaksi di-drop.
    </Fragment>

    <Fragment slot="solution">
      Ringkasan menghindari clone nama pelanggan. Compiler memastikan reference tetap valid selama view dipakai.
    </Fragment>
  </StudyCaseStep>
</StudyCase>

## Keadaan setelah Bab 10

- `PaymentMethod` menjadi trait untuk metode pembayaran.
- `Tunai` dan `Qris` mengimplementasikan trait itu.
- `proses_pembayaran<T: PaymentMethod>` adalah fungsi generik dengan trait bound.
- `Ringkasan<'a>` meminjam nama pelanggan dari `Transaksi` tanpa clone.
- `KasirError` dari Bab 9 tetap dipakai.
- Belum ada trait object `Box<dyn PaymentMethod>`; itu masuk Bab 18.
- Belum ada test otomatis; itu masuk Bab 11.

:::note[Kalau di bahasa lain]
Trait mirip interface TypeScript, Go, atau PHP. Bedanya, implementasi Rust ditulis eksplisit dan bisa memiliki default method. Lifetime tidak punya padanan langsung di JavaScript atau PHP. Ia menyatakan umur reference pada compile time, bukan mengandalkan garbage collector atau reference counting.
:::
