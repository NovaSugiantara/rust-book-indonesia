Thread memungkinkan beberapa bagian program berjalan bersamaan. Di server, satu thread bisa menangani request sementara thread lain menunggu database atau memproses antrean. Urutan eksekusi antar thread tidak dijamin.

## Membuat thread

<RustPlayground
  code={`use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..4 {
            println!("worker {i}");
            thread::sleep(Duration::from_millis(5));
        }
    });

    for i in 1..3 {
        println!("main {i}");
        thread::sleep(Duration::from_millis(5));
    }

    handle.join().unwrap();
}`}
  filename="src/main.rs"
  label="Thread baru dan main thread berjalan bersamaan"
/>

`thread::spawn` menerima closure dan mengembalikan `JoinHandle<T>`. Tanpa `join`, main bisa selesai lebih dulu dan mematikan thread yang masih berjalan. `join` memblokir thread pemanggil sampai thread target selesai.

Memindahkan `handle.join().unwrap()` sebelum loop main akan membuat main menunggu lebih dulu, sehingga output tidak lagi berselang-seling. Posisi `join` memengaruhi perilaku program.

## Meminjam data dari main thread

Closure yang membaca variabel dari main thread mencoba meminjamnya. Compiler menolak karena thread bisa hidup lebih lama dari data yang dipinjam.

<RustPlayground
  code={`use std::thread;

fn main() {
    let data = vec![1, 2, 3];

    let handle = thread::spawn(|| {
        println!("Data: {data:?}");
    });

    handle.join().unwrap();
}`}
  expectError
  filename="src/main.rs"
  label="Contoh error closure thread meminjam data main"
/>

Pesan `closure may outlive the current function, but it borrows data` muncul karena `thread::spawn` membutuhkan closure dengan umur `'static`. Compiler menyarankan `move`.

## move untuk memindahkan kepemilikan

<RustPlayground
  code={`use std::thread;

fn main() {
    let data = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("Data: {data:?}");
    });

    handle.join().unwrap();
}`}
  filename="src/main.rs"
  label="Closure move memindahkan data ke thread"
/>

Dengan `move`, thread memiliki `data`. Setelah itu, data tidak boleh dipakai lagi di main. Kalau tetap dipakai, compiler menolak:

<RustPlayground
  code={`use std::thread;

fn main() {
    let data = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("Data: {data:?}");
    });

    drop(data);

    handle.join().unwrap();
}`}
  expectError
  filename="src/main.rs"
  label="Contoh error memakai data setelah dipindahkan ke thread"
/>

Pesan `use of moved value: data` menunjukkan bahwa kepemilikan sudah berpindah. `move` tidak melanggar aturan ownership; ia hanya memindahkan data sehingga main tidak lagi berhak memakainya.

## Di backend

Pola thread per request mudah dipahami, tetapi setiap thread sistem operasi punya biaya. Server produksi biasanya memakai thread pool atau runtime async agar jumlah pekerjaan yang menunggu I/O tidak menghabiskan thread.

Thread tetap berguna untuk pekerjaan CPU-bound yang benar-benar paralel, misalnya kompresi, hashing, atau pemrosesan gambar. Untuk pekerjaan yang didominasi menunggu jaringan dan database, async sering lebih sesuai. Bab 17 membahas pilihan ini lebih lanjut.

:::note[Kalau di bahasa lain]
Go memakai goroutine yang dikelola runtime, bukan thread OS 1:1, dan channel sebagai alat komunikasi utama. Node.js memakai `worker_threads` untuk pekerjaan paralel; setiap worker punya isolate JavaScript sendiri dan berkomunikasi lewat pesan. Python memakai `threading`, tetapi pada CPython global interpreter lock membatasi eksekusi bytecode Python paralel dalam satu proses. Rust standard library memakai thread OS 1:1 dan memeriksa kepemilikan data antar thread saat kompilasi.
:::

:::tip[Tips]
Jangan menganggap menambah thread selalu mempercepat. Ukur beban kerja dan ingat biaya pembuatan thread. Untuk pekerjaan singkat dan sering, thread pool atau async task lebih masuk akal.
:::
